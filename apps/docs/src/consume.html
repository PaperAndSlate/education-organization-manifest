Consume

Read the graph carefully

A valid JSON document is only one part of a trustworthy consumer workflow. Validate each resource, preserve its identity and freshness, and distinguish authority from factual verification.

Discovery sequence

  1. Construct the origin’s HTTPS well-known URL. Do not accept an unrelated origin as the school’s identity.
  2. Fetch with bounded size, timeout, redirect, and DNS/private-network protections.
  3. Require the expected media type and parse strict JSON without duplicate keys.
  4. Validate the root, then independently validate linked resources and module indexes.
  5. Evaluate delegation before treating cross-origin resources as authorized.

Authority dimensions

Question Evidence Do not infer
Who controls the resource? HTTPS origin, root scope, delegation That the content is true
Who supplied the value? Source and provenance records That the source is authoritative for every field
Was it changed? Digest or optional signature That it is current or correct
Can it be shown to users? Privacy and review status That a private source may be copied publicly

HTTP and caching

Honor cache validators and declared expiry, but treat caches as transport behavior rather than authority. Revalidate redirects and final destinations. Never send cookies or credentials to a discovered endpoint. The local fetch helper implements these controls for tests and CLI use.

Failure handling

Findings have stable codes, categories, severity, JSON Pointers, related references, and remediation. A consumer should show actionable errors while keeping warnings distinct from invalidity. Unknown top-level fields are not silently accepted; namespaced extensions live under extensions.

A consumer is responsible for its own safety, privacy, and truthfulness decisions.
