# Maintainers and Succession

## Roles

- project lead;
- specification editor;
- schema maintainer;
- reference implementation maintainer;
- security contact;
- release manager;
- documentation/adoption lead;
- community moderator.

One person may initially hold several roles, but releases and security-sensitive changes should move toward two-person review.

## Maintainer criteria

- sustained contributions;
- protocol understanding;
- respectful review;
- security/privacy awareness;
- no unresolved conflicts of interest;
- acceptance of governance duties.

## Appointment/removal

Document public process, inactivity threshold, and emergency removal.

## Bus factor

Maintain:

- multiple GitHub owners;
- multiple domain/DNS administrators;
- release access recovery;
- security inbox access;
- package registry owner redundancy;
- IANA contact succession;
- offline recovery codes;
- repository mirrors.

## Change-controller continuity

IANA records and canonical URLs require durable contacts. Avoid a single personal email as the only controller.

## Foundation transition

If paper&slate ceases operation:

- publish transition notice;
- transfer domains/registrations to a suitable nonprofit/community entity;
- preserve immutable specs/schemas;
- protect protocol name from proprietary capture;
- document package ownership transfer.

## Conflicts of interest

Maintainers disclose vendor/employer interests when proposals directly advantage those systems.
